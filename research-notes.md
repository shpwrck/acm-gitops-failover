## 1. ACM hub backup & restore (cluster-backup-operator)

### Enabling and dependencies
- Enable by setting component `cluster-backup` to `enabled: true` under `spec.overrides.components` in the `MultiClusterHub` CR; the older `spec.enableClusterBackup` field "is no longer supported and is replaced by this component". Enable/disable any time by editing the MultiClusterHub. ("MultiClusterHub advanced configuration" → ClusterBackup; "Enabling the backup and restore operator") — IN#advanced-config-hub, BC#enabling-backup-restore
- The `cluster-backup` component is **disabled by default** (`Enabled: False` in the deployed-components table). ("MultiClusterHub advanced configuration") — IN#advanced-config-hub
- The operator "depends on the OADP Operator to install Velero, and to create a connection from the hub cluster to the backup storage location"; Velero runs the actual backup/restore. ("Backup and restore operator architecture") — BC#backup-restore-architecture
- OADP is auto-installed in the same namespace where `cluster-backup` is enabled — the backup component namespace is `open-cluster-management-backup`; the backup option stays `Pending` until OADP is installed there. Exception: on AWS STS hubs you must install OADP manually (ARN token). ("Installing the backup and restore operator" → Enabling the backup operator / Installing the OADP operator) — BC#enabling-backup-operator-clusters, BC#installing-the-oadp-operator
- You must create a storage-location `Secret` in the OADP namespace and a `DataProtectionApplication` CR (namespace `open-cluster-management-backup`) with a `backupLocations` entry (`default: true` for the default location); sample shows an AWS S3 bucket. Supported storage = Velero's "AWS S3 compatible backup storage providers" list in the OCP OADP docs. ("Creating the storage location secret"; "Creating a DataProtectionApplication resource"; Additional resources) — BC#creating-the-storage-location-secret, BC#creating-a-dataprotectionapplication-resource
- OADP version can be pinned/overridden with the MultiClusterHub annotation `installer.open-cluster-management.io/oadp-subscription-spec: '{"channel": "stable-1.4", ...}'` (also used for disconnected CatalogSource override). ("Installing a custom OADP version") — BC#installing-custom-oadp

### CRs
- Two CRs, both in namespace `open-cluster-management-backup`: `BackupSchedule.cluster.open-cluster-management.io` (v1beta1) to schedule backups, and `Restore.cluster.open-cluster-management.io` (v1beta1) to restore them. ("Backup and restore operator architecture") — BC#backup-restore-architecture
- `BackupSchedule` spec fields: `veleroSchedule` (cron, required), `veleroTtl` (optional; Velero default max 720h), `useManagedServiceAccount` (optional, enables auto-import of imported clusters), `paused`, `managedServiceAccountTTL` (default token validity = 2× `veleroTtl`). ("Scheduling backups"; "Enabling automatic import") — BC#using-backup-restore, BC#enabling-auto-import
- The `BackupSchedule` creates a set of Velero `schedule.velero.io` resources producing three backup groups: Credentials backup (`acm-credentials-schedule-<timestamp>`), Resources backup (`acm-resources-schedule-…` + generic `acm-resources-generic-schedule-…`), Managed clusters backup (`acm-managed-clusters-schedule-…` = only "resources that activate the managed cluster connection to the hub cluster where the backup is restored"). ("Backup files created by a ACM schedule") — BC#backup-files-created-by-a-schedule
- `Restore` spec: `veleroManagedClustersBackupName`, `veleroCredentialsBackupName`, `veleroResourcesBackupName`, each taking `latest` | `skip` | `<backup_name>`; plus `cleanupBeforeRestore` (`None` | `CleanupRestored` | `CleanupAll`), `syncRestoreWithNewBackups: true`, `restoreSyncInterval` (default check every 30 min), and Velero restore filters (`includedNamespaces`, `excludedResources`, …). Only one Restore can be active at a time; a Restore runs once unless syncing. ("Using the restore operation for backup types"; "Cleaning the hub cluster after restore"; "Restoring passive resources while checking for backups") — BC#restoring-backup-restore-operation, BC#clean-hub-restore, BC#restore-passive-resources-check-backups
- `BackupSchedule` statuses include `Enabled`, `FailedValidation`, `BackupCollision`, `Paused`. `BackupCollision` is set automatically when the latest backup in the shared storage location was written by a *different* hub — the resource then deletes its own Velero schedules to prevent data corruption. ("Scheduling backups" status table; "Preventing backup collisions") — BC#using-backup-restore, BC#prevent-backup-collision

### Passive hub pattern
- Active-passive: the active/primary hub manages clusters and backs up on schedule; passive hubs "continuously retrieve the latest backups and restore the passive data" using a `Restore` with `syncRestoreWithNewBackups: true`, standing by to become primary. "Active and passive hub clusters are connected to the same storage location." ("Configuring active-passive hub cluster" → Active-passive configuration) — BC#active-passive-config
- An active-passive configuration is optional: you can instead deploy a new hub at disaster time and restore everything (`restore-acm` with all three set to `latest`, `cleanupBeforeRestore: None` on a brand-new hub). ("Active-passive configuration" note; "Restoring all resources") — BC#active-passive-config, BC#restore-all-resources
- Failover is deliberately **not automated**: the admin decides that the primary is dead (vs. a network partition) and which passive hub becomes primary; after failover the admin manually creates a `BackupSchedule` on the new primary (the `backup-restore-enabled` policy / `backup-schedule-cron-enabled` template flags this; can be automated with Ansible job integration). ("Disaster recovery") — BC#disaster-recovery
- Version matching: "Ensure that the restore hub cluster uses the same ACM version that the backup hub cluster uses. You cannot restore a backup on a hub cluster with a version earlier than the one used by the backup hub cluster." To land on a newer version: install the same version, restore, then upgrade. ("Enabling the backup operator for your hub clusters"; "Running a restore operation on a hub cluster with a newer version") — BC#enabling-backup-operator-clusters, BC#run-restore-operation
- The restore hub must be configured **identically**: same ACM operator namespace, same additional operators installed (e.g. Ansible Automation Platform, OpenShift GitOps, cert-manager), same `MultiClusterHub`/`MultiClusterEngine` configuration, and a `DataProtectionApplication` pointing at the same storage location. ("Preparing the new hub cluster") — BC#prepare-new-hub
- Use a **new** (clean) hub for restore to avoid pre-existing data interfering; if reusing an existing hub that already manages clusters, `cleanupBeforeRestore: CleanupRestored` detaches restored-backup-managed clusters and cleans up their workloads, while user-created ManagedClusters (no `velero.io/backup-name` label) are left alone. ("Preparing the new hub cluster"; "Scenarios when using an existing hub cluster as a restore hub cluster") — BC#prepare-new-hub, BC#using-existing-hub

### What is / is not backed up
- Scope: "backup and restore support for all hub cluster resources, including managed clusters, applications, and policies" — hub *resources* only (managed-cluster workloads and PVs are not in scope; PV replication is the separate VolSync topic in the same guide). ("Backup and restore operator architecture"; "Business continuity") — BC#backup-restore-architecture, BC#business-cont-overview
- Backed up: all resources with API version suffix `.open-cluster-management.io` and `.hive.openshift.io`; plus API groups `argoproj.io`, `app.k8s.io`, `core.observatorium.io`, `hive.openshift.io` (so hub Argo CD `Application`/`ApplicationSet` CRs are included); `agent-install.openshift.io` and key Hive CRs (`clusterdeployment`, `machinepool`, `clusterpool`, `clusterclaim`, `clusterimageset`, `clustersync`) go into the `acm-managed-clusters-schedule` backup; Secrets/ConfigMaps with labels `cluster.open-cluster-management.io/type`, `hive.openshift.io/secret-type`, or `cluster.open-cluster-management.io/backup`. ("Resources that are backed up") — BC#backed-up-resources
- Excluded: everything in the `MultiClusterHub` namespace (hub-identity install resources); API groups `internal.`, `operator.`, `work.` (ManifestWork!), `search.`, `proxy.`, `action.`, `view.`, `clusterview.` `.open-cluster-management.io`, `admission.hive.openshift.io`, `velero.io`; and specific kinds (`clustermanagementaddon`, `backupschedule`, `restore`, `clusterclaim.cluster…`, `discoveredcluster`). ("Resources that are backed up") — BC#backed-up-resources
- Opt-in: label any third-party resource `cluster.open-cluster-management.io/backup: <any-string>` to include it (goes into `acm-resources-generic-schedule`); use value `cluster-activation` to defer its restore until managed-cluster activation. Hive `ClusterDeployment` secrets get the label automatically only when the cluster was created via console — GitOps-created Hive clusters need the label added manually. ("Resources that are backed up"; "Resources restored at managed clusters activation time") — BC#backed-up-resources, BC#resources-restored-managed-cluster-activation
- Activation set (backed up by `acm-managed-clusters-schedule`): `managedcluster.cluster…`, `klusterletaddonconfig.agent…`, `managedclusteraddon.addon…`, `managedclusterset(.cluster/.clusterview)…`, `managedclustersetbinding.cluster…`, `clusterpool/clusterclaim.hive…`, `clustercurator.cluster…`. ("Resources restored at managed clusters activation time") — BC#resources-restored-managed-cluster-activation
- Observability has its own separate backup/restore configuration topic. ("Backup and restore" topic list) — BC#backup-intro

### `veleroManagedClustersBackupName: latest` vs `skip`
- `veleroManagedClustersBackupName` "is used to define the restore option for the managed clusters activation resources". `latest` restores the last managed-clusters backup; `skip` "does not attempt to restore this type of backup" (no `restore.velero.io` created). ("Using the restore operation for backup types") — BC#restoring-backup-restore-operation
- Passive restore = `veleroManagedClustersBackupName: skip` + credentials/resources `latest`: hub gets secrets, ConfigMaps, apps, policies, and managed-cluster *passive* data but does **not** activate any connection — clusters "are still connected to the original hub cluster that created the backup files". ("Restoring passive resources"; "Scheduling backups" note) — BC#restore-passive-resources, BC#using-backup-restore
- Activation = set `veleroManagedClustersBackupName: latest`: "Immediately after the VeleroManagedClustersBackupName is set to latest, the managed clusters are activated on the new hub cluster and is now the primary hub cluster." Once activated, the Restore goes `Finished` and `syncRestoreWithNewBackups` is ignored. ("Restoring passive resources while checking for backups"; "Restoring activation resources") — BC#restore-passive-resources-check-backups, BC#restore-activation-resources
- Before activating on the passive hub, "shut down the previous hub cluster where the backup was created", otherwise its reconciliation tries to reimport/reclaim the managed clusters. ("Restoring activation resources"; "Scheduling backups" note) — BC#restore-activation-resources, BC#using-backup-restore
- Even with activation restored, only **Hive-created** managed clusters reconnect automatically (Hive stores the spoke kubeconfig in the cluster namespace, which is backed up; the import controller rewrites the spoke's bootstrap kubeconfig). **Imported** clusters show `Pending Import` and must be re-imported — unless auto-import via ManagedServiceAccount is enabled. ("Restoring imported managed clusters") — BC#restore-imported-managed-clusters
- Auto-import: enable `managedserviceaccount` component in `MultiClusterEngine` + `useManagedServiceAccount: true` on the `BackupSchedule`; the backup controller creates a `ManagedServiceAccount` named `auto-import-account` per imported cluster plus a `ManifestWork` installing a `klusterlet-bootstrap-kubeconfig` RoleBinding; on restore, the controller builds an `auto-import-secret` from the backed-up token for every `Pending Import` cluster. Caveats: token must be unexpired at restore time; non-OCP clusters need `spec.managedClusterClientConfigs.url` set on `ManagedCluster` or they stay `Pending Import`. ("Connecting clusters for backup by using a ManagedServiceAccount"; "Automatic import considerations") — BC#auto-connect-clusters-msa, BC#auto-import-considerations
- To keep the primary hub alive during a DR test: pause its `BackupSchedule` (`paused: true`), tag its resources by running a local `Restore` with `cleanupBeforeRestore: None` + all `latest`, and add annotation `import.open-cluster-management.io/disable-auto-import: ''` to each `ManagedCluster` so the old hub doesn't reclaim the clusters after they move. ("Running the restore operation while the primary hub cluster is active" → Preparing the primary hub cluster) — BC#keep-hub-active-restore-prepare

## 2. Managed cluster attachment mechanics during hub loss

### What happens when the hub dies
- "When the hub cluster fails, some features stop working, even if all managed clusters still work." Managed clusters and their workloads keep running; you need a recovery plan for the hub data. ("Backup and restore" intro) — BC#backup-intro
- Upstream OCM: the klusterlet registration agent on the spoke maintains the hub-side `ManagedCluster` and refreshes a heartbeat lease "on a one-minute basis" by default (interval controlled by `.spec.leaseDurationSeconds`); when heartbeats stop, `ManagedClusterConditionAvailable` becomes `Unknown` and the hub adds the `cluster.open-cluster-management.io/unreachable` taint. (Hub-side view of a lost link; the spoke agent's pull loop simply keeps retrying — the connection is client-initiated from the spoke.) — https://open-cluster-management.io/docs/concepts/cluster-inventory/managedcluster/
- ACM restore docs rely on this: after moving clusters to a new hub, the old hub shows the clusters' status as `Unknown`. **Constraint:** only delete a `ManagedCluster` from the old hub while its status is `Unknown` — "If the status is not Unknown, your workloads are uninstalled from the managed cluster" (deletion of a *connected* ManagedCluster triggers cleanup on the spoke). ("Cleaning up managed cluster resources on the backup hub cluster") — BC#keep-hub-active-restore-clean
- A running hub actively re-imports: "the previous hub cluster tries to reimport the managed clusters as soon as the managed cluster reconciliation finds that the managed clusters are no longer available" — hence the shut-down-the-old-hub requirement before activation restore, or the `import.open-cluster-management.io/disable-auto-import: ''` annotation. ("Scheduling backups" note; "Preparing the primary hub cluster") — BC#using-backup-restore, BC#keep-hub-active-restore-prepare

### Re-pointing a managed cluster to a NEW hub
- Documented path A (backup/restore): restore activation data (`veleroManagedClustersBackupName: latest`) on the new hub — Hive-created clusters reconnect automatically; imported clusters need MSA auto-import or manual re-import. ("Restoring imported managed clusters"; "Connecting clusters for backup by using a ManagedServiceAccount") — BC#restore-imported-managed-clusters, BC#auto-connect-clusters-msa
- Documented path B (manual): import the cluster on the new hub like any import — create the `ManagedCluster` CR + either an `auto-import-secret` (kubeconfig or token/server pair) in the cluster namespace, or apply the generated `klusterlet-crd.yaml` / `import.yaml` on the spoke. The auto-import secret is used once and deleted (keep it with annotation `managedcluster-import-controller.open-cluster-management.io/keeping-auto-import-secret`). ("Importing a managed cluster by using the CLI" → Importing a cluster by using the auto import secret) — CL#importing-clusters-auto-import-secret
- Upstream mechanics of hub switch: the spoke work agent evicts an `AppliedManifestWork` (and thus garbage-collects the resources it applied) in exactly two scenarios: "the manifestwork of the current appliedmanifestwork is missing on the hub, or the appliedmanifestwork hub hash does not match the current hub hash of the work agent" — i.e. after re-pointing to a new hub, ManifestWork-delivered resources the new hub does not re-create are removed after an eviction grace period. (`AppliedManifestWorkStatus.EvictionStartTime` API doc) — https://github.com/open-cluster-management-io/api/blob/main/work/v1/types.go
- The eviction grace period defaults to **60 minutes** (`AppliedManifestWorkEvictionGracePeriod: 60 * time.Minute`, agent flag `--appliedmanifestwork-eviction-grace-period`). Upstream source (not in ACM product docs — treat the exact default as upstream-verified only). — https://github.com/open-cluster-management-io/ocm/blob/main/pkg/work/spoke/options.go
- Related: `work.open-cluster-management.io` (ManifestWork) is an *excluded* API group in hub backups, so a restored hub does not restore ManifestWorks — the restored owner resources (apps, policies, addons) regenerate them. ("Resources that are backed up") — BC#backed-up-resources

### Detach/cleanup when the hub is unreachable (spoke-side cleanup)
- The documented situation list explicitly includes: "The hub that was managing the cluster was lost or destroyed before detaching the managed cluster, and there is no way to detach the managed cluster from the hub." ("Removing remaining resources after removing a cluster") — CL#removing-a-cluster-from-management-in-special-cases
- Documented manual cleanup on the spoke (with `oc` + spoke KUBECONFIG): (1) strip finalizers from the `klusterlet` CR (`oc get klusterlet … | xargs oc patch klusterlet --type=merge -p '{"metadata":{"finalizers": []}}'`); (2) `oc delete namespaces open-cluster-management-agent open-cluster-management-agent-addon --wait=false`; (3) delete + de-finalize all `open-cluster-management.io` CRDs; (4) verify namespaces and CRDs are gone. ("Removing remaining resources after removing a cluster") — CL#removing-a-cluster-from-management-in-special-cases

### Removing a ManagedCluster from the hub when the SPOKE is unreachable
- Normal removal: console Detach/Destroy, or CLI `oc delete managedcluster $CLUSTER_NAME`; detaching or destroying also deletes the cluster namespace on the hub ("Do not place custom resources in this namespace"). ("Removing a cluster from management"; "Removing a cluster by using the command line") — CL#remove-managed-cluster, CL#remove-a-cluster-by-using-the-cli
- If the namespace remains after removal (finalizers stuck because e.g. the spoke never confirmed cleanup): list leftover namespaced resources (`secrets`, `managedclusteraddons`, `manifestworks`, `appliedmanifestworks`, `leases`, `managedclusterinfo`, `clusteroauths`, roles/rolebindings…), edit each and delete the non-Kubernetes finalizers, then `oc delete ns <cluster-name>`. ("Troubleshooting namespace that remains after deleting a cluster") — CL#trouble-cluster-remove-namespace-mce
- Removing finalizers directly from a `Terminating` **ManagedCluster** object is documented in older ACM versions ("To delete a terminating managed cluster, manually remove the finalizers") — e.g. ACM 2.3 "Removing a cluster from management"; the 2.17 book only documents the namespace-level finalizer cleanup. **UNVERIFIED for 2.17** as an explicit step. — https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_management_for_kubernetes/2.3/html/clusters/remove-managed-cluster
- Detaching the hub's own `local-cluster` self-import is special: with default `disableHubSelfManagement: false` the hub re-imports itself automatically (can take hours; restarting the `multiclusterhub-operator` pod speeds it up). ("Removing a cluster by using the console") — CL#remove-a-cluster-by-using-the-cli

## 3. ACM + OpenShift GitOps integration

### GitOpsCluster CR and Placement-driven registration (push model)
- CR: `GitOpsCluster`, `apiVersion: apps.open-cluster-management.io/v1beta1`, with `spec.argoServer.cluster: <your-local-cluster-name>`, `spec.argoServer.argoNamespace: openshift-gitops`, and `spec.placementRef` → a `Placement` (cluster.open-cluster-management.io/v1beta1). "The referenced Placement resource must be in the same namespace as the GitOpsCluster resource." Registers the placement-selected managed clusters to that GitOps operator instance. ("Registering managed clusters to OpenShift GitOps operator") — GO#gitops-register
- Prerequisites: GitOps operator installed on the hub; clusters imported; a `ManagedClusterSet` + `ManagedClusterSetBinding` binding the set into the GitOps namespace; the `ManagedServiceAccount` add-on enabled "to rotate the token that is used for the Argo CD push and pull model". Only OCP clusters register by default; non-OCP clusters can be registered if `ManagedCluster.spec.managedClusterClientConfigs.url` is set (2.12+ import modes fill it automatically). ("Prerequisites"; "Registering non-OCP clusters") — GO#prerequisites-argo, GO#register-non-ocp
- Effect: "for every managed cluster that is bound to the GitOps namespace through the placement and ManagedClusterSetBinding custom resources, a secret with a token to access the ManagedCluster is created in the GitOps instance server namespace" (default `openshift-gitops`) — i.e. ACM manufactures the Argo CD cluster secrets. The token comes from the `ManagedServiceAccount` `application-manager` service account (cluster-admin on the spoke by default; customizable). ("OpenShift GitOps token") — GO#secret-gitops
- Secret contents priority order: (1) **cluster proxy service** (default; works for all Kubernetes clusters; server URL = cluster-proxy URL, caData from `openshift-service-ca`, bearer token = `application-manager` MSA token); (2) **managed cluster client configs** (direct API server endpoint + CA; OCP clusters only) when the `cluster-proxy` add-on is disabled. ("OpenShift GitOps token") — GO#secret-gitops
- Hub-failure implication (derived from the above, marked as derivation): the Argo CD cluster secrets, the `GitOpsCluster`, `Placement`, `ManagedClusterSetBinding`, and hub `ApplicationSet`/`Application` CRs all live on the hub; the hub backup includes `argoproj.io` and all `.open-cluster-management.io` resources, so a restored hub reconstructs the registration; push-model deployment stops while the hub (and its Argo CD) is down, but nothing removes the already-deployed spoke workloads (see §4 semantics). — BC#backed-up-resources (backup coverage), GO#secret-gitops

### ApplicationSet push vs pull model
- Both models use the same `ApplicationSet` CRD with the `clusterDecisionResource` generator referencing `configMapRef: acm-placement` and a `labelSelector` on `cluster.open-cluster-management.io/placement: <placement-name>`. ("Creating the ApplicationSet custom resource") — GO#crd-pull-model
- Push: "OpenShift GitOps applies resources directly from a centralized hub cluster to the managed clusters"; only the hub runs Argo CD, which "has credentials for managed clusters". Push is the default "unless you add the `apps.open-cluster-management.io/ocm-managed-cluster` and `apps.open-cluster-management.io/pull-to-ocm-managed-cluster` annotations". ("Architecture Push model") — GO#arch-push
- Pull: "the application resources are propagated by the Propagation controller to the managed clusters by using manifestWork"; each spoke's local Argo CD applies them ("An Argo CD server must be running on each target managed cluster"), destination is the local `https://kubernetes.default.svc`. Required template annotations/labels: `apps.open-cluster-management.io/ocm-managed-cluster: '{{name}}'`, `argocd.argoproj.io/skip-reconcile: "true"` (so the hub controller ignores it), label `apps.open-cluster-management.io/pull-to-ocm-managed-cluster: "true"`. ("Deploying Argo CD with Push and Pull model"; "Architecture Pull model"; "Creating the ApplicationSet custom resource") — GO#gitops-push-pull, GO#arch-pull, GO#crd-pull-model
- Pull prerequisites: GitOps operator installed on hub **and** every target spoke in `openshift-gitops`; hub GitOps operator ≥ 1.9.0 and hub version ≥ spoke versions; every managed cluster must have a cluster secret in the hub Argo namespace (created via `GitOpsCluster` + `Placement`) for the ApplicationSet controller to render per-cluster Applications; spoke `openshift-gitops-argocd-application-controller` needs cluster-admin (or per-namespace `managed-by` labels). ("Prerequisites") — GO#prereqs-pull-model
- Pull status reporting: `MulticlusterApplicationSetReport` (apps.open-cluster-management.io/v1alpha1), one per ApplicationSet in the same namespace, aggregates per-cluster resource lists, sync/health status and errors; built by the Resource sync controller + Aggregation controller (10s cycles) which run with the Propagation controller in the `multicluster-integrations` pod (hub). Status is "not real-time". ("MulticlusterApplicationSetReport") — GO#status-report
- Pull-model hub-failure behavior (derived): the hub-side Propagation/Aggregation controllers stop, so no new app updates propagate and no aggregated status; but the Application CR and workload already live on the spoke, where the local Argo CD keeps reconciling from Git independently ("Each managed cluster individually communicates with the GitHub repository to deploy the resource manifests locally"). Spoke-side removal of the delivered Application CR only happens via the AppliedManifestWork eviction scenarios in §2 (hub-hash change / work missing on a reachable hub), not merely because the hub is down. Red Hat's pull-model announcement still notes "the hub cluster itself still represents a potential single point of failure, which you should address through redundancy or other means." — GO#arch-pull, https://github.com/open-cluster-management-io/api/blob/main/work/v1/types.go, https://www.redhat.com/en/blog/introducing-the-argo-cd-application-pull-controller-for-red-hat-advanced-cluster-management

### GitOps add-on (installs GitOps on spokes)
- The GitOps add-on "automates the deployment and lifecycle management of OpenShift GitOps on the managed clusters", enabled via `GitOpsCluster.spec.gitopsAddon.enabled: true`. Modes: `Basic` (GitOps operator + ArgoCD instance on spokes; OLM-based install for OCP via `olmSubscription.enabled: true`) and `Agent` (Technology Preview; adds the Argo CD Agent). **Important:** "If you enable the GitOps add-on by using the GitOpsCluster custom resource, then the GitOpsCluster disables the Push Model for all applications." ("Managing the OpenShift GitOps add-on") — GO#manage-gitops-addon
- Basic mode: for each placement-selected cluster the controller creates `AddOnDeploymentConfig` + `ManagedClusterAddOn` in the cluster namespace; the add-on installs the GitOps operator in `openshift-gitops-operator` and an Argo CD instance in `openshift-gitops` on the spoke; a user-owned `ArgoCD` `Policy` (`<name>-argocd-policy`) is generated once for RBAC/customization. Basic (non-agent) pull model is OCP-managed-clusters only. ("Enabling OpenShift GitOps add-on without the Argo CD Agent") — GO#enable-gitops-addon-without-argocd
- Agent mode (TP): `gitopsAddon.argoCDAgent.enabled: true`, `mode: managed|autonomous` (default `managed`); the GitOpsCluster controller does PKI management, creates agent-mode Argo CD cluster secrets, dynamic `AddOnTemplate`, ManifestWorks propagating hub CA certs, and deploys the Argo CD Agent on each selected spoke; the agent principal runs on the hub (`openshift-gitops-agent-principal` pods); ApplicationSets route by `destination.name: '{{name}}'`. ("GitOps overview"; "Enabling OpenShift GitOps add-on with Argo CD Agent (Technology Preview)") — GO#gitops-overview, GO#enable-gitops-addon-with-argocd

## 4. Argo CD failover patterns generally

- App-of-apps: "one Argo CD app that consists only of other apps" — a parent Application points at a Git directory of Application manifests, declaratively bootstrapping the rest (so a replacement Argo CD instance can be rebuilt from Git by re-applying one root app). Cascading deletion requires the `resources-finalizer.argocd.argoproj.io` finalizer on child Applications; without a finalizer, deleting an Application does not delete its resources. ("Cluster Bootstrapping — App Of Apps Pattern") — https://argo-cd.readthedocs.io/en/stable/operator-manual/cluster-bootstrapping/
- ApplicationSet cluster generator: parameterizes Application templates from the Argo CD cluster secrets "in the Argo CD namespace" (params: `name`, `nameNormalized`, `server`, labels/annotations), supports `selector` with `matchLabels`/`matchExpressions`, and dynamically targets "both local and non-local clusters, for every cluster that matches the cluster selector" — adding/removing a cluster secret adds/removes apps. ("Cluster Generator") — https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Cluster/
- What happens when the Argo CD instance dies: the application controller is "a Kubernetes controller which continuously monitors running applications and compares the current, live state against the desired target state" and "optionally takes corrective action" — sync/prune are actions the controller performs. With the controller gone, deployed workloads are ordinary Kubernetes resources on the target cluster and keep running; nothing prunes them. (Derived from the architecture doc — the docs contain no single explicit "workloads keep running" sentence; **the derivation itself is UNVERIFIED as a doc quote**.) ("Architectural Overview — Application Controller") — https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/
- Prune semantics: "By default (and as a safety mechanism), automated sync will not delete resources when Argo CD detects the resource is no longer defined in Git." Deletion requires `spec.syncPolicy.automated.prune: true` (or manual sync with prune). So a restored/replacement Argo CD with prune disabled will only flag OutOfSync; with `prune: true` it will delete live resources absent from Git on the next sync. ("Automated Sync Policy — Automatic Pruning") — https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/
- Self-heal semantics: "By default, changes that are made to the live cluster will not trigger automated sync"; enabling `spec.syncPolicy.automated.selfHeal: true` makes Argo CD sync whenever "the live cluster's state deviates from the state defined in Git" — i.e. a replacement Argo with selfHeal+prune converges the cluster to Git, reverting drift accumulated while Argo was down. ("Automated Sync Policy — Automatic Self-Healing") — https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/
- Cluster secrets: each target cluster is a Secret in the Argo CD namespace labeled `argocd.argoproj.io/secret-type: cluster`, with stringData `name`, `server` (API URL), and `config` (JSON: `bearerToken`, `tlsClientConfig`, `username/password`, `awsAuthConfig`, `execProviderConfig`, …). The in-cluster destination is `https://kubernetes.default.svc`. A new Argo CD instance is given target-cluster credentials by (re)creating these secrets — manually, via `argocd cluster add`, declaratively from Git, or (with ACM) automatically by the `GitOpsCluster` controller from Placement decisions with rotated `application-manager` MSA tokens (see §3). ("Declarative Setup — Clusters") — https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/#clusters, GO#secret-gitops
- Argo CD state backup: `argocd admin export > backup.yaml` / `argocd admin import - < backup.yaml` (run with the matching image version, `-n` for non-default namespace) — Argo CD state is Kubernetes resources (Applications, config/secrets), so in a git-as-source-of-truth setup export/import is largely unnecessary; re-bootstrap from Git + recreate cluster secrets achieves the same end state. ("Disaster Recovery") — https://argo-cd.readthedocs.io/en/stable/operator-manual/disaster_recovery/
- ACM 2.17's hub backup explicitly includes the `argoproj.io` API group, so hub-resident Applications/ApplicationSets ride along in the ACM hub backup (Argo CD operator itself must be pre-installed on the restore hub — listed as an example operator to install before restoring). — BC#backed-up-resources, BC#prepare-new-hub
- OpenShift GitOps ↔ OCP 4.21 compatibility: GitOps 1.20.4 is available on OCP 4.14, 4.16–4.21; GitOps 1.21.0 on OCP 4.14, 4.16–4.22. ("Red Hat OpenShift GitOps release notes", 1.20 / 1.21) — https://docs.redhat.com/en/documentation/red_hat_openshift_gitops/1.20/html/release_notes/gitops-release-notes, https://docs.redhat.com/en/documentation/red_hat_openshift_gitops/1.21/html/release_notes/gitops-release-notes

## Cross-cutting facts a failover guide should carry

- One hub per cluster: "You can only have one single ACM hub cluster installation on each OpenShift cluster." ("Preparing for ACM installation") — IN#prepare-install-acm
- The passive hub must have the **same operators** installed (including OpenShift GitOps) *before* restore. — BC#prepare-new-hub
- Backup collision protection exists (`BackupCollision` status) but the docs still instruct: stop/pause the old hub's `BackupSchedule` (or the hub itself) before restoring managed-cluster data elsewhere. — BC#understand-backup-collision, BC#prevent-backup-collision
- After failover, creating the `BackupSchedule` on the new primary is a manual step (policy `backup-restore-enabled` / template `backup-schedule-cron-enabled` reports if you forget). — BC#disaster-recovery
- A full return-to-primary procedure exists (backup on the secondary, pause, disable-auto-import annotations, restore with `CleanupRestored` on the original hub). ("Restoring data to the initial hub cluster") — BC#restore-data-initial-hub

## 6. Public recommendations: which failover pattern do the docs actually endorse?

- **Active-passive backup/restore is the productized, explicitly documented hub-DR pattern.** The ACM Business Continuity guide's "Configuring active-passive hub cluster" and "Disaster recovery" sections ARE the official recommendation (BC#active-passive-config, BC#disaster-recovery). Reinforced by the Red Hat blog series "RHACM: High availability and disaster recovery" parts 1-3 (standard Active/Standby, primary + N standbys, continuous restore from shared S3; best practice: "regularly restore backups and activate a hub cluster standby") — https://www.redhat.com/en/blog/rhacm-high-availability-and-disaster-recovery-part-1 (also part-2, part-3), and "Backup and Restore Hub Clusters with RHACM" — https://www.redhat.com/en/blog/backup-and-restore-hub-clusters-with-red-hat-advanced-cluster-management-for-kubernetes
- **Git-as-source-of-truth / decentralized sync is endorsed as a resilience principle, not as the hub-DR product.** The pull-model announcement itself concedes: "the hub cluster itself still represents a potential single point of failure, which you should address through redundancy or other means" — https://www.redhat.com/en/blog/introducing-the-argo-cd-application-pull-controller-for-red-hat-advanced-cluster-management. The Argo CD Agent (TP in ACM 2.17 gitopsAddon agent mode) is marketed as removing "the control plane as a single point of failure" — https://developers.redhat.com/blog/2025/10/06/using-argo-cd-agent-openshift-gitops. Argo CD's own DR doc treats Argo state as rebuildable from git (admin export/import) — https://argo-cd.readthedocs.io/en/stable/operator-manual/disaster_recovery/
- **The two patterns are explicitly composed in Red Hat's Nov 2025 blog "Argo CD Disaster Recovery strategy using RHACM and OADP"** — https://www.redhat.com/en/blog/argo-cd-disaster-recovery-strategy-using-red-hat-advanced-cluster-management-and-oadp — Argo CD runs on BOTH hubs; ACM backup carries `argoproj.io` resources; **gotcha: Argo repositories/ConfigMaps/Secrets are NOT in the default backup scope** and must be labeled `cluster.open-cluster-management.io/backup: argocd`; an ACM policy acts as "admission controller" mutating `AppProject` resources on the passive hub to inject a deny `SyncWindow` (24h) so the passive Argo cannot sync; failover = remove sync-block policy, remove Restore, create BackupSchedule on the new primary (reverse to fail back).
- **No public reference architecture recommends pure active-active dual hubs (git only, no backup/restore).** The pieces are all documented, but the composition is not a blessed pattern; every official DR text routes hub redundancy through backup/restore.
